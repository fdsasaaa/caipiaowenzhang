# Daily Partial Batch Retention (V3 Policy)

## Policy Authority Order

```
1. User's latest explicit decision (always wins)
2. Canonical handoff / project state document
3. Current main policy file (policies/DAILY_WEBSITE_READY_PRODUCTION.json)
4. Current tests on main
5. Historical docs / website downstream contracts
```

When a conflict exists between these layers, the higher layer takes precedence.
A PR that changes the policy file (layer 3) must not silently break the
user's explicit decision (layer 1) or the canonical handoff (layer 2).

## V3 Retention Semantics

### Core Constants

```
FORMAL_RETENTION_MINIMUM = 1
OPERATIONAL_REFILL_TARGET = 10
TARGET = 20
```

### Status Decision Table

| Qualified (website-ready) | Status                        | Manifest | Discard? |
|---------------------------|-------------------------------|----------|----------|
| 0                         | BLOCKED_BELOW_MINIMUM         | No       | N/A      |
| 1-9                       | PASS_PARTIAL_QUALITY_FIRST    | Yes       | **No**   |
| 10-19                     | PASS_PARTIAL_QUALITY_FIRST    | Yes      | **No**   |
| 20+                       | PASS_TARGET                   | Yes      | No       |

### What Each Constant Means

- **FORMAL_RETENTION_MINIMUM (minimum=1)**: The formal commit floor.
  Below this, production fails closed. At or above this, ALL qualified
  articles are retained and a manifest is written. This is NEVER a discard
  threshold — it is the minimum number of qualified articles that must
  exist for the day to count as "produced."

- **OPERATIONAL_REFILL_TARGET (operational_minimum=10)**: A production
  health signal. If the daily run produces 1-9 articles, the system still
  retains them (partial_batch_retention=true) but flags the day as
  "below_operational_minimum" in the report. This signals that the refill
  loop should be investigated — it is NOT a reason to discard articles.

- **TARGET (target=20)**: The ideal daily volume. Reaching this status
  changes the report to PASS_TARGET.

### What Changed From V2

| Field                          | V2 (pre-V3)   | V3 (current)   |
|--------------------------------|---------------|----------------|
| version                        | 2             | 3              |
| minimum                        | 10            | 1              |
| operational_minimum            | (absent)      | 10             |
| partial_batch_retention        | (absent)      | true           |
| Behavior: 6 qualified articles | BLOCKED → discard | PASS_PARTIAL → retain |

### POLICY_OSCILLATION Prevention

The policy invariant guard (`assert_v3_policy_invariant`) runs BEFORE
any AI generation in both the CI test suite and the production workflow.
If the policy does not match V3 semantics, it fails immediately with
`POLICY_INVARIANT_VIOLATION` — no AI budget is spent.

This permanently prevents the oscillation pattern (#101 -> #102 -> #103
-> #104: minimum=1 -> 10 -> 1 -> 10) because any revert to minimum=10
will be caught before production starts.

### Generation Result Recovery

If article-level production passes but repository audit or pytest fails,
all generated artifacts (Approved JSON, public-r1, manifest, report,
registry delta) are preserved on a `recovery/*` branch. This prevents
the Run 33366804177 scenario where 6 qualified articles were discarded
because the workflow reset/clean deleted the generated bytes.

Recovery branches are preserved WITHOUT:
- Merge to main
- Website intake
- Scheduling
- Publishing

They exist solely for manual review and potential re-staging.
